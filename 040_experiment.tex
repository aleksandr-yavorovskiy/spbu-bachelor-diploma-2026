Для проведения эксперимента была создана тестовая таблица, состоящая из 10 столбцов и 100 миллионов строк, занимающая 12Гб места на диске. \todo{Схема таблицы? Ссылка на код заполнения?} Такие размеры необходимы для того, чтобы показать преимущество использования \pgduckdb{}: чем больше данных, тем эффективнее работа \pgduckdb{} при \olap{}-нагрузке. Эти данные также были конвертированы в формат данных \parquet{} с использованием \pgparquet{} --- итоговый .parquet файл занимает 2Гб дискового пространства. \todo{Файлы в формате .csv и .parquet, содержащие тестовые данные, можно найти по ссылке...}

При проведении серии экспериментов сравнивались следующие три различные конфигурации:
\begin{enumerate}
    \item \enquote{\postgresql{}}~--- \enquote{классический} \postgresql{} версии 18.1 без аналитических расширений, работающий с данными, представленными в стандартном для \sql{} \todo{виде (таблицах);}
    \item \enquote{\pgduckdb{} и таблица}~--- \postgresql{} с использованием расширения \pgduckdb{} (в конфигурации \postgresql{} предварительно устанавливается \todo{опция} \foreignquote{english}{pgduckdb.force\_execution=true}), запросы всё так же выполняются над таблицей;
    \item \enquote{\pgduckdb{} и \parquet{}}~--- \postgresql{} с использованием расширения \pgduckdb{}, запросы выполняются над .parquet файлом.
\end{enumerate}

При сравнении скорости работы различных подходов использовались следующие запросы:
\begin{enumerate}
    \item аналитический запрос, использующий оконные функции \todo{сноска/ссылка(https://postgrespro.ru/docs/postgrespro/current/tutorial-window)}, сортировку и группировку значений;
    \item фильтрационный запрос, использующий построенные индексы;
    \item \todo{обычный \enquote{SELECT *} запрос}.
\end{enumerate}
