\subsection{\oltp{}, \olap{} и \htap{}}
\oltp{} (Online Transaction Processing, интерактивная транзакционная обработка) является методом организации работы \dbms{}, при котором данные обрабатываются преимущественно через большое количество кратких транзакций, каждая из которых выполняет небольшие операции чтения и записи. Преимуществами данного подхода являются целостность данных в любой момент времени и надёжность системы, достигаемые благодаря использованию транзакций, обеспечивающих свойства ACID (Atomicity, Consistency, Isolation, Durability). Эти свойства гарантируют, что каждая транзакция выполняется полностью или не выполняется вовсе, данные остаются согласованными, параллельные транзакции не мешают друг другу, а изменения сохраняются даже при сбоях системы. Однако существенным недостатком \oltp{}-парадигмы является неоптимизированность для выполнения аналитических запросов над большими массивами данных, так как системы ориентированы на быстрое выполнение маленьких транзакций, а не на обработку больших наборов информации.

В свою очередь \olap{} (Online Analytical Processing, интерактивная аналитическая обработка) ориентирована на анализ больших массивов данных и сложные запросы, включающие агрегации, группировки и вычисления статистик.

Один из способов организации работы с информацией состоит из нескольких этапов:
\begin{enumerate}
    \item \oltp{}-система \enquote{собирает} данные путем выполнения большого количества коротких транзакций;
    \item затем полученная информация обрабатывается и конвертируется в формат, удобный для аналитики (например, \parquet{}), с использованием процессов ETL (Extract, Transform, Load), которые извлекают, преобразуют и загружают данные в \olap{}-хранилище;
    \item после чего \olap{}-система производит необходимую аналитическую обработку данных.
\end{enumerate}

Такой подход имеет определённые недостатки: получение ответа на интересующие вопросы происходит с задержкой, так как данные сначала нужно собрать и преобразовать; необходимо хранить данные в разных форматах, что может занимать десятки или сотни гигабайт памяти и влечёт дополнительные расходы на её поддержку; также стоит отметить, что сам процесс конвертации может приводить к значительным затратам вычислительных ресурсов системы.

\htap{} (Hybrid Transaction/Analytical Processing, гибридная транзакционная/аналитическая обработка) объединяет возможности \oltp{} и \olap{} в одной системе, позволяя одновременно выполнять транзакционные и аналитические запросы над одними и теми же данными. Это сокращает задержку получения аналитических результатов и устраняет необходимость в регулярной конвертации и дублировании данных. Основные преимущества \htap{} включают более оперативное принятие решений, снижение затрат на хранение данных и упрощение архитектуры информационных систем \cite{HtapDbPaper}.


\subsection{Обзор используемых технологий}
\subsubsection{\postgresql{}}
\postgresql{} \cite{postgresqlDocumentation}~--- объектно-реляционная \dbms{} с открытым исходным кодом, поддерживающая расширяемость, большой набор типов данных и стандарты SQL. Данное ПО активно используется как для \oltp{}-так и для \olap{}-нагрузок в различных приложениях благодаря своей стабильности, производительности и надежности.

\postgresql{} использует хранение данных по строкам (т.н. \foreignquote{english}{row-oriented storage}), при котором таблица хранится на диске как последовательность строк. Такой подход оптимален для транзакционных рабочих нагрузок (\oltp{}), где преобладают операции вставки, обновления и выборки отдельных строк. Однако для аналитических задач (\olap{}), требующих обработки больших массивов данных и выполнения агрегатных запросов по столбцам, row-oriented хранение является менее эффективным по сравнению с column-oriented решениями, при которых данные из таблицы хранятся на диске не по строкам, а по столбцам.


\subsubsection{Формат данных \parquet{}}
\parquet{} (также \apacheparquet{}) \cite{apacheParquetDocumentation} является колоночно-ориентированным форматом хранения данных, первоначально созданным в 2013 году для \apachehadoop{}\footnote{Набор программных решений для работы с Big Data. URL: \url{https://hadoop.apache.org/} (дата обращения: \DTMdate{2025-12-30}).}. Со временем данный формат стал широко использоваться во многих аналитических системах (на\-пример, \apachespark{}, \googlecloudstorage{}, \wikiparq{} \cite{WikiParqPaper}) ввиду того, что его архитектура позволяет значительно сжимать размер файлов и ускорять обработку данных за счёт колоночного хранения и эффективного кодирования значений.

Само содержание файла \parquet{}, представленное на Рис. \ref{fig:parquetFileLayout}, можно разбить на следующие части: заголовок, \todo{\enquote{несущая} информация (row groups и column chunks)} и метаданные. Благодаря файлу parquet.thrift\footnote{URL: \url{https://github.com/apache/parquet-format/blob/master/src/main/thrift/parquet.thrift} (дата обращения \DTMdate{2025-12-30}).}, являющемуся частью спецификации формата \cite{apacheParquetSpecification} и содержащему детальное описание структуры \parquet{} файла, можно провести более подробный разбор данного \todo{формата}.

Заголовок файла содержит \enquote{магическое число} (Magic number), т.н. \foreignquote{english}{PAR1}~--- четырёхбайтовое значение, \todo{позволяющее системе однозначно идентифицировать формат файла}.

\enquote{Несущая} информация состоит из следующих компонентов:
\begin{itemize}
    \item \textbf{Row groups} (группы строк)~--- горизонтальные фрагменты таблицы данных, каждый из которых содержит набор строк для эффективной пакетной обработки.
    \item \textbf{Column chunks} (колоночные \todo{чанки})~--- вертикальные сегменты внутри row group, содержащие данные одного столбца; каждый column chunk хранит данные отдельно, что позволяет выполнять операции агрегации и выборки по столбцам более эффективно.
    \item \textbf{Page} (страница)~--- минимальная единица хранения данных внутри column chunk. Страница содержит \todo{набор} значений одного столбца и необходимую информацию для корректного чтения и декодирования данных. Основные компоненты страницы:
        \begin{itemize}
            \item \textbf{Page header}~--- заголовок страницы, который содержит информацию о типе страницы, количестве значений, размере закодированных данных и других параметрах, необходимых для декодирования и навигации внутри файла.
            \item \textbf{Repetition levels}~--- \todo{дописать}
            \item \textbf{Definition levels}~--- \todo{дописать}
            \item \textbf{Values}~--- \todo{сами закодированные данные столбца} изначальной таблицы.
        \end{itemize}

        Страницы бывают следующих типов:
        \begin{itemize}
            \item \textbf{DATA\_PAGE}~--- \todo{основная страница с данными, содержит значения столбца, закодированные по выбранной схеме;}
            %\item \textbf{DATA\_PAGE\_V2}~--- улучшенная версия DATA\_PAGE, более компактно хранит repetition и definition levels, снижая накладные расходы и ускоряя чтение;
            \item \textbf{DICTIONARY\_PAGE}~--- \todo{страница, содержащая словарь уникальных значений для column chunk; используется при dictionary encoding для уменьшения размера файла;}
            \item \textbf{INDEX\_PAGE}~--- \todo{страница с индексами, позволяющая быстро находить нужные диапазоны данных внутри column chunk, ускоряя выполнение аналитических запросов.}
        \end{itemize}
\end{itemize}

Блок метаданных, называемый \foreignquote{english}{footer} (\enquote{нижняя сноска}), располагается после \enquote{несущей} информации и включает:
\begin{itemize}
    \item версию формата;
    \item схему таблицы;
    \item пары ключ/значение (key/value pairs) для хранения дополнительной информации;
    \item метаданные для каждой row group, содержащие, в свою очередь, метаданные для каждого column chunk, включая статистику: минимальное и максимальное значения, количество null-значений, количество различных значений;
    \item длину footer, \todo{позволяющую корректно прочитать файл с конца}.
\end{itemize}
