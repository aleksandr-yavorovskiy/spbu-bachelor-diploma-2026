\section{Обзор}
\label{sec:relatedworks}

\subsection{\oltp{}, \olap{} и \htap{}}
\oltp{} (Online Transaction Processing, интерактивная транзакционная обработка) является методом организации работы \dbms{}, при котором данные обрабатываются преимущественно через большое количество коротких транзакций, каждая из которых выполняет небольшие операции чтения и записи. Преимуществами данного подхода являются целостность данных в любой момент времени и надёжность системы, достигаемые благодаря свойствам ACID (Atomicity, Consistency, Isolation, Durability). Эти свойства гарантируют, что каждая транзакция выполняется полностью или не выполняется вовсе, данные остаются согласованными, параллельные транзакции не мешают друг другу, а изменения сохраняются даже при сбоях системы. Однако существенным недостатком \oltp{}-парадигмы является неоптимизированность для выполнения аналитических запросов над большими массивами данных, так как системы ориентированы на быстрое выполнение маленьких транзакций, а не на обработку больших наборов информации.

В свою очередь, \olap{} (Online Analytical Processing, интерактивная аналитическая обработка) ориентирована на анализ больших массивов данных и сложные запросы, включающие агрегации, группировки и вычисления статистик.

Один из способов организации работы с информацией состоит из нескольких этапов:
\begin{enumerate}
    \item \oltp{}-система \enquote{собирает} данные путем выполнения большого количества коротких транзакций;
    \item затем полученная информация обрабатывается и конвертируется в формат, удобный для аналитики (например, \parquet{}), с использованием процессов ETL (Extract, Transform, Load), которые извлекают, преобразуют и загружают данные в \olap{}-хранилище;
    \item после чего \olap{}-система производит необходимую аналитическую обработку данных.
\end{enumerate}

Такой подход имеет определённые недостатки: получение ответа на интересующие вопросы происходит с задержкой, так как данные сначала нужно собрать и преобразовать; необходимо хранить данные в разных форматах, что может занимать десятки или сотни гигабайт памяти и влечёт дополнительные расходы на её поддержку; также стоит отметить, что сам процесс конвертации может приводить к значительным затратам вычислительных ресурсов системы.

\htap{} (Hybrid Transaction/Analytical Processing, гибридная транзакционная/аналитическая обработка) объединяет возможности \oltp{} и \olap{} в одной системе, позволяя одновременно выполнять транзакционные и аналитические запросы над одними и теми же данными. Это сокращает задержку получения аналитических результатов и устраняет необходимость в регулярной конвертации и дублировании данных. Основные преимущества \htap{} включают более оперативное принятие решений, снижение затрат на хранение данных и упрощение архитектуры информационных систем \cite{HtapDbPaper}.


\subsection{Обзор используемых технологий}
\subsubsection{\postgresql{}}
\postgresql{} \cite{postgresqlDocumentation}~--- объектно-реляционная \dbms{} с открытым исходным кодом, поддерживающая расширяемость, большой набор типов данных и стандарты \sql{}. Данное ПО активно используется для выполнения \oltp{}- и \olap{}-нагрузок в различных приложениях благодаря своей стабильности, производительности и надежности.

\postgresql{} использует хранение данных по строкам (т.н. \foreignquote{english}{row-oriented storage}), при котором таблица хранится на диске как последовательность строк. Такой подход оптимален для транзакционных рабочих нагрузок (\oltp{}), где преобладают операции вставки, обновления и выборки отдельных строк. Однако для аналитических задач (\olap{}), требующих обработки больших массивов данных и выполнения агрегатных запросов по столбцам, row-oriented хранение является менее эффективным по сравнению с column-oriented решениями, при которых данные из таблицы хранятся на диске не по строкам, а по столбцам.


\subsubsection{Формат данных \parquet{}}
\parquet{} (также \apacheparquet{}) \cite{apacheParquetDocumentation} является колоночно-ориентированным форматом хранения данных, первоначально созданным в 2013 году для \apachehadoop{}\footnote{Набор программных решений для работы с Big Data. URL: \url{https://hadoop.apache.org/} (дата обращения: \DTMdate{2025-12-30}).}. Со временем данный формат стал широко использоваться во многих аналитических системах (на\-пример, \apachespark{}, \googlecloudstorage{}, \wikiparq{} \cite{WikiParqPaper}) ввиду того, что его архитектура позволяет значительно сжимать размер файлов и ускорять обработку данных за счёт колоночного хранения и эффективного кодирования значений.

Само содержание файла \parquet{}, представленное на Рис. \ref{fig:parquetFileLayout}, можно разбить на следующие части: заголовок, основная информация и метаданные. Благодаря файлу \mbox{parquet.thrift}\footnote{URL: \url{https://github.com/apache/parquet-format/blob/master/src/main/thrift/parquet.thrift} (дата обращения \DTMdate{2025-12-30}).}, являющемуся частью спецификации формата \cite{apacheParquetSpecification} и содержащему детальное описание структуры \parquet{} файла, представляется возможным проведение более подробного разбора его составляющих.

Заголовок файла содержит \enquote{магическое число} (Magic number), т.н. \foreignquote{english}{PAR1}~--- четырёхбайтовое значение, позволяющее системе однозначно идентифицировать формат файла.

Основная информация файла \parquet{} состоит из следующих компонентов:
\begin{itemize}
    \item Row groups (группы строк)~--- горизонтальные фрагменты таблицы данных, каждый из которых содержит набор строк для эффективной пакетной обработки.
    \item Column chunks (фрагменты столбцов)~--- вертикальные сегменты внутри row group, содержащие данные столбцов таблицы; каждый column chunk хранит данные отдельно, что позволяет выполнять операции агрегации и выборки по столбцам более эффективно.
    \item Page (страница)~--- минимальная единица хранения данных внутри column chunk. Страница содержит набор значений одного столбца и необходимую информацию для корректного чтения и декодирования данных. Основными компонентами страницы являются:
        \begin{itemize}
            \item Page header~--- заголовок страницы, который содержит информацию о типе страницы, количестве значений, размере закодированных данных и других параметрах, необходимых для декодирования и навигации внутри файла.
            \item Definition levels и repetition levels (уровни определения и уровни повторения)~--- вспомогательные последовательности целых чисел, используемые для кодирования вложенных и повторяющихся структур данных согласно алгоритму, предложенному в статье о принципах работы аналитической системы \mbox{\dremel{} \cite{DremelPaper}}. Совместное использование данных уровней позволяет представлять вложенные структуры (например, массивы или \json{}-структуры) в виде столбцов без потери информации о самой структуре данных и связях между ее элементами.
            \item Values~--- часть самих данных столбца изначальной таблицы.
        \end{itemize}

        Сами страницы бывают следующих типов:
        \begin{itemize}
            \item Data Page (страница данных)~--- основная страница с данными, содержит непосредственно значения столбца таблицы.
            \item Dictionary Page (страница словаря)~--- страница, содержащая словарь уникальных значений для column chunk; используется при словарном кодировании (dictionary encoding) для уменьшения размера файла.
            \item Index Page (страница индекса)~--- страница, хранящая информацию об индексах, которые позволяют быстро находить нужные диапазоны данных внутри column chunk, тем самым ускоряя выполнение аналитических запросов.
        \end{itemize}
\end{itemize}

Блок метаданных, называемый \foreignquote{english}{footer} (\enquote{нижняя сноска}), располагается после основной информации и включает:
\begin{itemize}
    \item версию формата;
    \item схему таблицы;
    \item пары ключ/значение (key/value pairs) для хранения дополнительной метаинформации;
    \item метаданные для каждой группы строк и каждого фрагмента столбца:
    \begin{itemize}
        \item статистические: минимальное и максимальное значения, количество различных значений и null-значений;
        \item какой алгоритм сжатия использовался для данной части данных;
        \item используемая кодировка.
    \end{itemize}
\end{itemize}

Для уменьшения объема хранимых данных \parquet{} поддерживает следующие алгоритмы сжатия информации:
SNAPPY, GZIP, LZO, BROTLI, ZSTD, LZ4 и пришедший ему на смену в версии 2.9 формата алгоритм LZ4\_RAW.

\subsubsection{\duckdb{}}
\duckdb{} \cite{duckdbDocumentation}~--- это колоночно-ориентированная реляционная \dbms{}, оптимизированная для выполнения \olap{}-нагрузок. В отличие от традиционных серверных \dbms{}, \duckdb{} является встраиваемой (in-process) системой, не требующей отдельной серверной части для обработки запросов, что, в свою очередь, позволяет уменьшить накладные расходы при взаимодействии с теми системами, в которые \duckdb{} встраивается.

Для разбора и анализа \sql{}-запросов \duckdb{} использует библиотеку \libpgquery{} \cite{libpgquery}, предоставляющую доступ к \postgresql{}-парсеру, благодаря чему достигается высокая степень совместимости синтаксиса и упрощается перенос запросов между системами.

Для разработчиков \duckdb{} предоставляет программный интерфейс (DuckDB \api{}), позволяющий использовать систему из различных языков программирования, включая \texttt{C}, \texttt{C++}, \texttt{Python}, \texttt{Java} и \texttt{Rust} \cite{duckdbApi}. Данное \api{} дает возможность взаимодействовать с \dbms{} \duckdb{} посредством установки соединения, конфигурирования, выполнения \mbox{\sql{}-запросов} и обработки результатов.



\subsection{Обзор существующих решений}
\subsubsection{\pgparquet{}}
\pgparquet{} \cite{pgparquet}~--- расширение \postgresql{}, предназначенное для интеграции СУБД с форматом данных \parquet{}. Данное программное решение позволяет выполнять копирование данных из \parquet{} файлов в таблицы \postgresql{} и, наоборот, записывать данные из \postgresql{} в формат \parquet{} с использованием доработанных стандартных команд \foreignquote{english}{COPY TO} и \foreignquote{english}{COPY FROM}. При эскпортировании в \parquet{} также доступен выбор одного из алгоритмов сжатия, подддерживаемых форматом. Кроме взаимодействия с локальным сервером, данное расширение позволяет обмениваться данными с облачными хранилищами.

Помимо операций импорта и экспорта данных, \pgparquet{} предоставляет возможность чтения метаданных файлов \parquet{}, включая описание схемы, статистические характеристики столбцов и информацию о структуре row groups и column chunks.

\subsubsection{\pgduckdb{}}
\pgduckdb{} \cite{pgduckdb} является расширением, интегрирующим аналитический движок \duckdb{} непосредственно в \postgresql{}, что позволяет производить высоконагруженную \olap{}-обработку внутри самой \dbms{} без необходимости выгрузки данных во внешние аналитические системы или использования отдельного сервиса. Кроме работы с таблицами \postgresql{}, данное ПО предоставляет возможность прямого чтения данных из Data Lake и файлов формата \parquet{}, включая файлы, размещённые в удалённых (remote) объектных хранилищах, таких как Amazon S3, Google Cloud Storage, Azure Blob Storage и \mbox{Cloudflare R2}.

Ключевой особенностью \pgduckdb{} является использование векторизованного аналитического движка \duckdb{} для выполнения \mbox{\olap{}-запросов}. В отличие от стандартного исполнителя \postgresql{}\footnote{\postgresql{} Executor. URL: \url{https://www.postgresql.org/docs/current/executor.html} (дата обращения: \DTMdate{2026-01-15}).}, обрабатывающего данные построчно, \duckdb{} работает с векторами значений, что позволяет существенно сократить накладные расходы на обработку строк и повысить производительность при сканировании и агрегации больших объёмов данных.

В то же время данное расширение имеет ряд ограничений; одним из самых существенных является невозможность использования \duckdb{} внутри определяемых пользователем функций (user-defined functions\footnote{\postgresql{} Documentation. User-Defined Functions. URL: \url{https://www.postgresql.org/docs/current/xfunc.html} (дата обращения: \DTMdate{2026-01-15})}). При попытке вызова такой функции будет выведено сообщение: \mbox{\foreignquote{english}{ERROR:  DuckDB execution is not supported inside functions}.}


\subsubsection{\parquetfdw{}}
Еще одно расширение \postgresql{}, предоставляющее возможности для работы с файлами формата \parquet{},~--- \parquetfdw{} \cite{parquetfdw}~--- представляет собой реализацию механизма Foreign Data Wrapper\footnote{\postgresql{} Wiki. Foreign Data Wrappers. URL: \url{https://wiki.postgresql.org/wiki/Foreign_data_wrappers} (дата обращения: \DTMdate{2026-01-15}).} (\enquote{обертка сторонних данных}), обеспечивающую взаимодействие с \parquet{} файлами как с внешними таблицами. Одним из главных преимуществ данного ПО является отсутствие неоходимости предварительной загрузки данных в \db{}, то есть процесс импорта \parquet{} файлов, происходящий в расширении \pgparquet{}, здесь не нужен; за счет такого архитектурного решения появляется возможность уменьшить использование дискового пространства и вычислительных ресурсов системы, которые обычно затрачиваются при конвертации данных в нативные таблицы.

После создания внешней таблицы при помощи \parquetfdw{} пользователь может выполнять все стандартные операции аналитической обработки данных.


\subsection{Выводы}

В вопросе организации обработки данных существуют два различных подхода~--- \oltp{} и \olap{}; в современном мире важны и надежность транзакций, и возможность быстро анализировать большие объемы информации, и потому существует тенденция по объединению данных парадигм в рамках одного инструмента и создания гибридных (\htap{}) систем.

\parquet{} широко используется в современных аналитических системах благодаря внутренней архитектуре файла данного формата, стремящейся обеспечить максимальную оптимизацию для колоночной обработки данных. Аналитический движок \duckdb{} позволяет взаимодействовать с данными, хранящимися в формате \parquet{}, и хорошо приспособлен для \olap{}-нагрузок.

Благодаря тому, что \postgresql{} является \dbms{} с открытым исходным кодом и поддерживает расширяемость, существует ряд решений, предоставляющих возможности для взаимодействия с файлами \parquet{} непосредственно из данной \dbms{}.
